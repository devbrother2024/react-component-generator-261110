# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번엔 예외"라고 판단하지 않는다.

## 1. 적용 기준

### TDD를 반드시 적용하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API** (엔드포인트, 요청/응답 처리, 에러 매핑)
- **유틸리티 / 순수 함수** (파싱, 정규화, 변환)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)
- **훅 / 상태 로직** (UI와 분리된 동작)

### TDD가 불필요한 대상

- **타입 정의** (`type`, `interface` 선언만 있는 파일)
- **설정 파일** (`package.json`, `tsconfig`, `vite.config`, `eslint.config` 등)
- **순수 UI** (스타일, 레이아웃, 마크업만 바뀌는 변경)
- **SQL / 마이그레이션 스크립트**
- **문서, 주석, 문구 수정**

경계가 모호하면 **적용하는 쪽**으로 판단한다.

## 2. RED - GREEN - REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 문장으로 설명한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 문법 오류, import 오류, 오타, 잘못된 셋업으로 인한 실패는 RED가 아니다. 테스트를 고치고 다시 실행한다.
- 이미 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 고친다.

### GREEN: 최소한의 코드로 통과

- **테스트를 통과시키는 최소한의 코드만** 작성한다.
- **YAGNI.** 테스트가 요구하지 않는 분기, 옵션, 추상화, 확장 포인트를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 테스트를 실행해 확인한다.
- 테스트를 통과시키려고 테스트를 약화하거나 수정하지 않는다.

### REFACTOR: green 상태에서 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **항상 green 유지.** 리팩터링 중간마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

- 다음 동작이 남아 있으면 **다시 RED로 돌아간다.** 한 번에 여러 동작을 구현하지 않는다.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 재시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 포함한다.
- 삭제 후에는 테스트에서 요구하는 코드만 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드도 깨진다. 테스트는 30초면 쓴다. 단순할수록 비용이 낮다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 통과하는 코드에 맞춰진다. 실패를 본 적 없으므로 무엇도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정에 드는 시간이 더 길다. TDD가 더 빠른 경로다. |
| "삭제하면 낭비다" | 매몰비용 오류다. 검증되지 않은 코드를 유지하는 쪽이 더 큰 비용이다. 삭제하고 RED부터 다시 한다. |
| "프로토타입이다" | 프로토타입은 그대로 프로덕션이 된다. 적용 대상이면 예외는 없다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 있으면 **그 규칙이 이 파일보다 우선한다.**
- **이 파일은 기본값(fallback)이다.** 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
