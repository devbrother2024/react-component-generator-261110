# commit: 변경사항 분석 후 컨벤션 커밋

## 커밋 메시지 컨벤션

```
<type>: <요약>

<본문 (선택)>
```

- type: `feat`(기능 추가), `fix`(버그 수정), `refactor`(동작 변화 없는 구조 개선), `chore`(설정·의존성·빌드·문서 등 기타)
- 요약: 한국어, 한 줄, 50자 안팎, 마침표 없음. "무엇을 했는지"를 현재형 명사구/동사구로 쓴다. (예: `feat: 결과 카드에 폴더 탭 UI 추가`)
- 본문: 요약만으로 부족할 때만 쓴다. "왜 바꿨는지"를 중심으로 한다.
- 세션에 커밋 attribution 지침(Co-Authored-By 등)이 주어져 있으면 메시지 끝에 그대로 붙인다.

## 절차

### 1. 변경사항 분석

저장소 여부와 상태를 먼저 확인한다. `git`이 아니면 중단하고 사용자에게 알린다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 톤 참고
```

- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- untracked 파일은 내용을 읽어서 포함 여부를 판단한다.
- `.env`, 키·토큰·인증서, 빌드 산출물(`dist/`, `node_modules/`) 등 커밋하면 안 되는 파일이 보이면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 목적(기능, 버그, 리팩터링, 설정)을 하나의 커밋으로 묶는다.
- 서로 다른 type이 섞여 있으면 커밋을 나눈다. 같은 파일 안에서 목적이 섞여 있으면 `git add -p` 대신 파일 단위로 묶는다.
- 단일 목적이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.
- 커밋마다 포함할 파일 목록과 type을 정한다.

### 3. 커밋 메시지 작성

각 단위마다 위 컨벤션으로 메시지를 작성한다. diff에 실제로 있는 내용만 쓰고, 추측으로 의도를 지어내지 않는다.

### 4. 승인 없이 바로 커밋

사용자 승인을 기다리지 않고 바로 커밋한다. 커밋하기 전에 계획을 아래 형식으로 짧게 출력해 무엇을 커밋하는지 남긴다.

```
커밋 1/2: feat: 결과 카드에 폴더 탭 UI 추가
  - src/components/ComponentCard.tsx
  - src/App.css

커밋 2/2: chore: 갈무리 폰트 CDN 링크 추가
  - index.html
```

- 커밋 단위별로 지정한 파일만 `git add <파일>`로 스테이징하고 커밋한다. `git add -A`, `git add .`는 쓰지 않는다.
- 같은 파일 안에서 목적이 섞여 있어 나누는 방법이 불분명하면, 그 경우에 한해 하나의 커밋으로 묶고 메시지 본문에 그 사실을 적는다.
- 훅이 실패하면 `--no-verify`로 우회하지 말고 원인을 고친 뒤 새 커밋으로 만든다.
- 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여준다.
- push는 사용자가 따로 요청할 때만 한다.
